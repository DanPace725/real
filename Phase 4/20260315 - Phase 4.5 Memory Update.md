# Phase 4.5 Memory Generalization Update

**Date:** March 15, 2026
**Context:** This update documents the Phase 4 memory revision work completed after reviewing Phase 7 and deciding that memory should be treated as a structural part of the generalized REAL architecture rather than an optional add-on.

---

## Why this update happened

Phase 4 successfully generalized the REAL loop across domains, but it did so with a thin memory model:

- episodic history
- consolidation as retention/pruning

Phase 7 developed a stronger account of memory:

- memory is maintained constraint, not just retained record
- slow-layer state should shape observation, cost, and reachable state
- cross-session continuity should be part of the core architecture

The purpose of this update was not to fully finish that merge, but to revise Phase 4 so it has the right architecture for that merge to continue cleanly.

---

## What changed conceptually

Phase 4 is now being treated as if memory has three layers:

1. **Episodic trace**
   Raw cycle history and trail data.

2. **Consolidated memory**
   Retained structure from experience, prepared for warm starts and later promotion.

3. **Maintained substrate**
   Slow-layer infrastructure that can, in later steps, modulate perception, cost, and policy.

This means Phase 4 is no longer conceptually organized around "engine + adapters + episodic log." It is now organized around "engine + adapters + memory stack," even though the richer substrate effects are still only partially activated.

## Core milestones completed

### M1: Memory-aware types and protocols

The generalized core now has explicit types and interfaces for substrate-aware memory work.

Updated:

- [types.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/types.py)
- [interfaces.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/interfaces.py)

- `SessionCarryover`
- `MemoryActionSpec`
- `MemorySubstrateProtocol`

This did not change engine behavior. It created the interface surface needed for the deeper memory model.

### M2: Separate episodic memory from generalized memory

The memory layout in `real_core` was split so episodic memory is no longer pretending to be the whole memory architecture.

Added:

- [episodic.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/episodic.py)
- [patterns.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/patterns.py)

Changed:

- [memory.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/memory.py) is now a compatibility shim re-exporting `EpisodicMemory`

This gives Phase 4 a real place for:

- episodic trace
- pattern primitives
- a neutral slow-layer substrate scaffold

### M3: Neutral substrate-capable engine path

The core engine was updated so it can now host substrate-aware behavior without requiring it.

Updated:

- [engine.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/engine.py)

New optional engine inputs:

- `substrate`
- `memory_binding`
- `consolidation_pipeline`
- `session_budget`

New neutral capabilities:

- substrate-modulated observation path
- memory-side action vocabulary
- optional budget filtering
- routing of memory actions through bindings
- optional substrate health influence on coherence input
- post-cycle substrate update path

Important: when none of those new parts are supplied, the engine still behaves like the old Phase 4 engine.

### M4: Cross-session carryover as a first-class core feature

Cross-session warm starts are no longer just a future idea. The core now has a standard carryover path.

Added:

- [consolidation.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/consolidation.py)
- [session_state.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/session_state.py)

Extended:

- [engine.py](C:/Users/nscha/Coding/Relationally%20Embedded%20Allostatic%20Learning/Phase%202/Phase%204/real_core/engine.py)

New capabilities:

- export `SessionCarryover`
- load `SessionCarryover`
- save carryover through `SessionStateStore`
- restore carryover through `SessionStateStore`
- use a default `BasicConsolidationPipeline` when no custom pipeline is supplied

This does not yet implement the full Phase 7 promotion logic, but it establishes the correct generalized mechanism for warm starts and future substrate promotion.

## What remains intentionally unfinished

This update was deliberately scoped to generalization architecture, not to a full memory-domain rollout.

Still pending:

- domain-specific `DomainMemoryBinding` implementations
- richer promotion logic from episodic retention into substrate structure
- config-level wiring for substrate and carryover in all experiment paths
- full domain migration through the memory-aware engine path
- more meaningful downstream testing in the richer Phase 5 / Phase 6 / future environments

That is intentional. The goal here was to make Phase 4 philosophically and structurally correct before pushing deeper into domain behavior.

---

## Current architectural state

Phase 4 now has:

- a generalized REAL engine that can still run in its original simple form
- a clearer memory stack in `real_core`
- neutral substrate and pattern primitives
- explicit memory-aware protocols
- a cross-session state format and persistence path

In other words, Phase 4 is no longer blocked by its old memory abstraction. It now has the architectural shape needed to absorb the stronger memory theory developed in Phase 7.

---

## Why this matters

This update brings the generalized core into better alignment with the project's philosophy.

Before this work, Phase 4 generalized the loop but not the full meaning of memory.

After this work, Phase 4 still does not fully realize memory as maintained constraint, but it now has:

- the right conceptual model
- the right module boundaries
- the right interfaces
- the right carryover mechanism

That makes future domain work much cleaner, and it avoids having Phase 7 remain a detached experimental branch with no path back into the generalized architecture.

## Light verification

Verification was intentionally light.

- the new and modified core files were syntax-checked with `py_compile`
- the default no-substrate Phase 4 engine path was smoke-tested after the engine refactor
- a small carryover save/load round-trip was run after the session-state work

No broad testing campaign was done in this update, by design.

Phase 4.5 so far is not a finished feature set. It is a memory-architecture correction.

- episodic trace
- consolidated carryover
- slow-layer substrate scaffold

That is the main result of this update.
